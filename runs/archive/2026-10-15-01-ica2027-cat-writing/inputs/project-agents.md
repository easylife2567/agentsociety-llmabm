# AGENTS.md：AgentSociety项目统一工作规范

> 本规范定义 Codex、Claude及受委派子agent在本项目中的共同工作方式，适用于软件开发和科研实验。**默认按用户要求直接处理当前项目；只有用户明确要求“创建一个 run”（或同样明确的新建 run 指令），才进入新 run 的工作流。**具体技术方法由仓库的 Skills 和专属文档规定。
>
> **最高原则：不得自作主张创建 run。** run 是用户主动开启的隔离探索空间，不是任何开发、修复、优化或实验任务的必经流程。**在已获授权的 run 中，探索可自由试错，但候选成果不得自动进入主项目。**

本文件以用户提供的原始AGENTS.md为主体，补充AgentSociety研究工作流。**项目根目录只维护这一份正文；`CLAUDE.md`是指向`AGENTS.md`的兼容链接，内容完全相同，不维护工具专属版本。** 研究问题见[TOPIC.md](TOPIC.md)，目录导航见[README.md](README.md)。

本地上游[AgentSociety2/AGENTS.md](AgentSociety2/AGENTS.md)和[架构说明](AgentSociety2/CLAUDE.md)是引擎参考文档，不是本课题的另一套规范。其源码仓库布局、远端、默认模型、自动提交建议不直接套用到本项目。系统与平台约束、用户明确指令优先；技能不得扩大用户授权。

## 1. 工作模式与边界

- **普通模式（默认）**：未明确要求创建或使用 run 时，在当前项目的正常工作区按用户授权执行任务。小修改、常规开发、测试和实验**不需要 run**，不得为它们自动新建 run、run README、run 索引或隔离 worktree。用户要求修改代码时，可直接修改授权范围内的正式文件并验证；不需要再请求一次“落地”授权。
- **run 模式（显式启用）**：仅当用户明确下令**创建新 run**时，才可新建 `runs/YYYY-MM-DD-NN-NAME/`；随后该 run 按“隔离探索 → 验证与审查 → 用户授权 → 选择性正式落地 → 归档”执行。对已有 run 的继续工作，必须由用户指明该 run，或由正在进行的连续对话明确指向它；不得因为任务类似就擅自续接其他 run。
- **主工作区与正式资产**：主工作区是用户正在使用的当前项目工作目录，其中的源码、测试、配置、文档、数据等均受任务授权范围约束。**普通模式允许在授权范围内直接修改；run 模式的探索阶段默认不得修改它们。**
- **run 内资产**：该 run 的 README、计划、报告、证据索引、专属脚本以及隔离探索环境，都是候选成果；不因已被创建、测试通过或提交到仓库，就自动成为正式项目资产。
- **正式落地与归档**：正式落地是把用户选定的 run 成果应用到主工作区的正式位置；归档只是结束 run 并保存有价值的记录。两者互不等同，归档不代表采用。

## 2. 用户指令与操作权限

| 用户请求 | 可以做 | 不能擅自做 |
| --- | --- | --- |
| “看看、分析、审查、盘点、规划、给方案” | 只读调查并回答 | 创建 run、修改文件、删除、commit、push 或同步 |
| “修复、实现、修改、优化 X”（未指定 run） | **普通模式**：在用户授权范围内直接修改当前项目，执行必要验证并报告结果 | 创建 run、将无关文件纳入修改、commit、push 或同步 |
| “尝试、探索、做实验”（未指定 run） | **普通模式**：按现有项目机制开展请求范围内的非破坏性尝试、实验和记录 | 创建 run；把模糊的试验请求自动理解为允许破坏性修改正式资产 |
| **“创建一个 run 来做 X”** | **新建 run**，建立 README；按需求创建隔离环境并在其中工作 | 未获落地授权就修改主工作区正式资产、commit、push 或同步 |
| “继续这个 run / 在指定 run 中做 X” | 仅继续明确指向的已有 run，更新其记录并在隔离环境中工作 | 新建另一个 run，或自动修改主工作区正式资产 |
| “把这个 run 的成果落地” | 选择性应用已确认成果到正式项目并验证 | 自动 commit、push、同步或归档无关 run |
| “归档这个 run” | 检查并整理该 run、保全证据、归档与更新索引 | 新建 run、自动落地、commit、push |
| “归档并 commit 这个 run” | 归档并精确提交已确认成果；必要落地只执行已明确采用并授权的部分 | 新建 run、声称未通过的验收已通过、push 或跨端同步 |
| “commit / 提交当前修改” | 精确检查并提交已获授权的修改，无论是否存在 run | 自动创建 run、push 或跨端同步 |

- **创建 run 是独立授权**：任务复杂、需要多轮对话、出现失败、需要保存证据、存在相似活跃 run，或者用户说“修复/优化/实验/继续/归档/commit”，**都不构成新建 run 的授权**。绝不因为 Codex 判断“用 run 更好”而替用户创建。
- **不凭空切换模式**：未明确进入 run 时始终按普通模式工作；进入已有 run 必须有明确的上下文指向。用户提出一个新的普通任务，不因仓库中存在活跃 run 就将其放入 run。
- **含糊的探索请求**：能安全进行的调查和验证直接进行；若必须隔离修改而当前尚无授权 run，应说明需要隔离及可选办法，**不得先斩后奏创建 run**。也不得将此当作擅自修改正式资产的许可。
- 只读请求不授权写入；修改请求只授权其相关文件和操作。用户已有未提交改动、无关任务文件和暂存内容始终不可擅自覆盖、清理或提交。
- `commit`、`push`、跨端同步、危险删除及 Git 历史改写分别遵守明确授权边界，不能相互推定。

**典型路径：**

- 用户说“修复 X” → 检查当前工作区 → 在授权范围内直接修复、测试并报告；**不创建 run**。
- 用户说“研究一下 X” → 只读调查或按授权做非破坏性实验并报告；**不创建 run**。
- 用户说“创建一个 run 研究 X” → 建立 run 和隔离环境 → 在其中探索、验证并记录 → 用户明确要求落地时才修改正式项目 → 需要时归档。

## 3. 仅在已授权的 run 中：如何隔离探索

### 3.1 新建与继续

1. **新建的唯一前提是用户明确要求创建 run。** 不得把“实施类任务开始”当作自动建 run 的触发器，也不得因没有匹配的活跃 run 而新建。若用户仅指定继续已有 run，不得再创建新 run。
2. 获得新建授权后，创建 `runs/YYYY-MM-DD-NN-NAME/README.md`，记载**目标与边界、当前阶段、资产及证据位置、已验证事实、待办与下一步**；在该 run 的 `.gitignore` 中忽略 `workspace/` 和 `tmp/`，更新 `runs/README.md`。
3. 记录探索所依据的代码版本和主工作区开始时的 Git 状态；已有未提交修改时，不擅自覆盖、清理或自动带入探索基线。若用户仅要求“创建一个 run”，则只做必要的创建与初始化，不自行开始额外的实现工作。

### 3.2 创建隔离探索环境

- **凡是在 run 中需要修改、编译或运行现有项目代码的探索，默认使用 `runs/<run-id>/workspace/` 下的独立 Git worktree**，而不是直接编辑主工作区的正式路径。
- 典型命令：`git worktree add --detach runs/<run-id>/workspace HEAD`。它从指定提交创建独立工作目录；其中的修改不会自动同步回主工作区。
- 创建前确认本 run 的 `.gitignore` 已忽略 `workspace/` 和 `tmp/`（可用 `git check-ignore` 核验），避免把完整副本误提交。**目录被 Git 忽略不表示其中的成果或证据可以随意删除。**
- 若探索依赖主工作区未提交的修改，先记录差异及风险；未经授权不自动带入 worktree。不能建立可靠隔离环境时，不得改为直接在主工作区试错，应说明阻碍。
- 纯文档推演、一次性脚本或不依赖完整项目的研究可直接在 run 内操作，无须强制创建 worktree。

### 3.3 探索可写范围与安全

- 默认只写**当前指定 run** 的内容及隔离工作区，并按需维护 `runs/README.md` 等任务索引；主工作区的其他正式文件只读。
- 可以在隔离环境中试验不同方案、修改模块副本、测试并记录失败；默认不擅自切换共享分支、commit、merge 或 push。注意命令的工作目录，防止脚本通过绝对路径或共享输出写回主工作区。
- 不得把生产服务、正式数据库、共享数据集的可写接口等有外部副作用的资源当作自由探索环境，除非获得单独授权并具备隔离或回退措施。
- `tmp/` 仅存放确认可删除的缓存与一次性文件。重要原始数据、日志、失败证据和结论依据须保留并索引；不能仅凭“不进 Git”判断其可以删除。
- 在正式落地前检查主工作区 Git 状态：除本 run 的记录与索引外，不应有因探索导致的正式资产修改；发现意外差异须核查而非默认接受。

### 3.4 基线与独立恢复材料

每个代码探索 run 必须记录准确的 Git commit 基线，并在 run 内保存从该基线恢复候选成果所需的完整材料。**独立恢复是指：不依赖原 `workspace/`、主工作区未提交修改或其他活跃 run，也能重新应用成果并开展离线验证。**

- **已有代码**：保存相对于记录的恢复起点的最终 `.patch`，遵循第 8.1 节；没有前置修改时，恢复起点就是 commit 基线。只包含本 run 的最终改动，不把多轮试错补丁当作最终交付。
- **其他文件操作**：保存新增代码、配置、脚本等文件的最终副本，并记录目标路径；删除、重命名和必要的非代码修改须有明确清单及恢复材料。未跟踪文件不会自动进入 `git diff`，必须单独核对。
- **必要输入与证据**：保存恢复需要的非敏感输入、依赖版本、操作顺序、验证命令及实际结果。大型数据可以引用有校验和的稳定冻结资产，并说明获取方式；凭据只记录配置方法，不复制到恢复包。
- **基线外依赖**：只有获准纳入的主工作区未提交修改，才能作为单独的前置恢复材料保存，并说明来源及应用顺序；不得把其他任务的差异混入成果。确需依赖其他成果时，必须明确其固定版本与材料位置，不能声称当前 run 可独立恢复。
- **README 交接**：在 run README 中集中说明基线、资产清单、应用顺序、验证结果、已采用和未采用部分。开始时可只初始化这些信息；候选成果交付及归档前必须补齐并实际核验恢复能力。

这些材料用于逐个审查、重新应用和测试成果，**不授权 agent 重置主工作区或删除无效 run**。历史 run 仅在用户明确要求继续或归档时按实际需要补齐，不自动批量改造。

## 4. 仅在 run 模式：成果如何正式落地

**run 的探索、验证通过及归档均不自动授权正式落地。以下流程仅在用户明确要求采用 run 成果时执行；普通模式下授权的直接修改不适用这一额外落地环节。**

1. **选择成果**：确定要采用的机制、文件和必要测试；不带入失败方案、临时依赖或无关中间态。
2. **核对最新状态**：比较候选成果与主工作区当前代码、未提交修改，不用探索开始时的旧版本覆盖现状。
3. **最小化应用**：只将已选定修改应用于正式位置，不直接整体复制/合并隔离工作区；已有代码通过第 8.1 节的 `.patch` 应用，新增文件按清单放到正式路径。基线与当前主工作区不同或存在相关未提交修改时，先核对差异并适配补丁，在实际目标状态执行 `git apply --check`；不得强行覆盖或把补丁适配当作扩大采用范围的授权。保留原候选补丁，并记录实际落地版本及差异。
4. **在正式位置验证**：执行与最终差异相符的必要测试、构建或实验；不能用隔离环境中的通过结果冒充正式位置的验证结果。
5. **记录边界**：在该 run README 中记录正式资产路径、结果、证据与限制；正式运行不应长期依赖活跃 run 的私有路径。

审查与验证的通用规则见第 5 节，不因进入 run 模式就自动提高审查强度。

## 5. 验证与审查：适度、基于证据（两种模式通用）

- **按实际风险选择强度**：小范围、低风险任务以定向检查和必要测试为主，不强制正式方案、独立子 Agent 审查、全量测试或额外报告。涉及真实的安全、隐私、数据损坏、不可逆操作、关键接口兼容性或重要结论有效性风险时，才按影响扩大审查与验证。
- **只审查相关问题**：关注本次变更实际引入、暴露或加重的缺陷，以及明确的验收要求；不把无关旧问题、可选重构、风格偏好、假设性的未来需求或纯粹的“万一”当作阻塞项。发现无关问题可以简要告知，不擅自扩大修改范围。
- **有依据地提出问题**：审查意见应说明具体位置、触发条件、实际影响和可核查的依据。区分已复现问题、有明确机制支撑的风险和纯粹猜测；不能因为想象出一种极端情况就要求新增防御代码或测试。
- **严格界定阻塞项**：只有明确影响任务验收、正确性或现有行为，或存在可信触发路径且后果严重的安全、隐私、数据损坏等风险，才阻止交付。低概率不自动等于高风险，也不自动等于零风险；以发生条件、证据和后果综合判断。其他建议标记为非阻塞，不以“风险尚未全部归零”为由反复拖延。
- **有限度地完成审查**：发现实质问题时优先采取最小修复和定向复验；达到约定验收条件、没有未解决的实质阻塞项后即可结束，不额外制造审查轮次或不断提高验收门槛。未运行的验证应如实说明，不得声称已经通过。

## 6. 文档、证据与长期知识

- **存在 run 时**：每个 run 的 README 是唯一实时状态与交接入口，并维护本级资产索引；`runs/README.md` 只索引活跃 run，`runs/archive/README.md` 只索引已归档 run。没有 run 的普通任务不需要为了记录进度而新建 run 或这些索引。
- **索引按层维护**：更新 README 前先阅读本级及上一级 README；资产增删、迁移或用途变化时更新所属层级索引，只有上一级的直接资产名称、用途或状态也变化时才同步上一级。根 README 维护项目定义与一级导航，不重复维护各 run、实验的实时进度；无关的历史索引问题不自动扩大本次修改范围。
- 按**问题和主题**组织方案、说明与验证报告，不按会话、日期或实验参数点重复新建。简单任务可直接在交付说明中总结；复杂任务按需要在已有文档体系中记录依据、实际结果、失败经验和证据位置。
- 整理后的报告表达当前有效结论，不混入无关中间实现；不得为了整洁而覆盖原始实验记录、重要失败证据或历史决策依据。
- 重要工程决策、研究认识和失败经验应沉淀至项目已有的知识入口，回指原始证据；不强制新增研究或工程管理目录。
- 具体代码规范、实验复现、测试流程与专用环境操作遵循仓库 Skills 和专属文档，AGENTS 不替代它们。

## 7. 归档、清理与 Git 操作

### 7.1 归档前提与结果标记

- **只有用户明确指定归档的已有 run 才能归档。** 探索结束、测试通过、成果已落地或已 commit，均不构成自动归档授权；不得为了满足“归档”或“commit”先创建 run。普通任务不需要 run 归档流程。
- 归档与采用分开记录：在 run README 中说明目标完成情况、实际验证、已采用部分的正式路径、未采用部分及限制。结果可以是已采用、部分采用、未采用或中止；未达到验收条件可以归档，但不得标为通过。

### 7.2 归档操作顺序

1. **盘点与保全**：先确认没有仍在使用该 run 的运行进程或不可迁移的依赖；无法解决时保留原位置并说明归档未完成，不清理工作区或移动活跃输出。核对第 3.4 节的基线、最终补丁、新增文件、其他恢复材料及重要证据。检查 worktree 的已跟踪、未跟踪和被忽略资产；不能仅保存 `git diff` 就宣称材料完整。需保留的文件移出 `workspace/` 和 `tmp/` 并纳入本级索引。
2. **核验恢复**：在本 run 的干净隔离工作区中，按 README 从记录的基线恢复成果，检查补丁可应用性、新增文件完整性并执行必要离线验证。已有记录只有在材料和候选版本一致时才可复用；恢复验证不自动授权重跑 LLM 仿真或扩大实验预算。无法验证时明确缺项与限制，不声称可完整恢复；若尚不能确认恢复材料完整，则保留原工作区及证据，暂停后续清理和迁移。
3. **解除 worktree 登记**：确认重要材料已保全后，使用 Git worktree 管理命令安全移除该 run 的隔离工作区；不能先删除目录再留下失效登记。若 Git 因未提交或未跟踪文件拒绝移除，先核查并保全剩余内容，不直接加 `--force` 绕过；确认可恢复后，才可清理该 run 已保全的探索差异以解除登记。不得清理其他任务的环境，或对整个项目使用全局 clean/reset。
4. **迁移与清理**：通常将该 run 移至 `runs/archive/<原 run-id>/`，保留原编号，避免改名造成历史引用混乱。仅清理确认可丢弃的缓存及临时文件；`tmp/` 内的日志如是重要证据必须先保全。
5. **更新索引与引用**：从活跃索引移除该 run，在 `runs/archive/README.md` 登记，并更新受迁移影响的导航、相对链接及恢复说明。实验冻结配置、manifest、checkpoint、原始日志中的历史路径属于原始证据，不批量改写；通过归档 README 说明旧路径与新位置的对应关系。正式代码、配置和启动入口不得继续依赖已清理的 run 私有路径。
6. **最终核对**：检查归档资产、链接和 Git 状态，确认本次操作只影响指定 run、必要索引及已授权的正式成果。未采用成果留作历史材料，不自动应用；归档本身不包含 commit、push 或同步。

### 7.3 Git 与交付

- **无论是否使用 run**，只有用户授权 commit 时才能提交；检查暂存区并精确暂存本任务相关修改，不使用 `git add .` 混入无关文件。commit 使用中文 Conventional Commits，正文说明原因、影响与验证。commit 不包含 push 或跨端同步。
- 交付时说明实际改动、验证结果、是否影响正式资产、证据与限制，以及当前 Git 状态；有 run 时另外说明其状态和归档位置。

## 8. 通用工作原则

- **回答要让用户听懂**：面向用户的回复、解释、报告和交接说明优先使用通俗、准确、直接的中文。先说结果和结论，再解释关键原因、影响与下一步；少用晦涩术语、套话和不必要的长篇铺垫，但不省略会影响判断的条件与限制。
- **专业术语首次出现要解释**：涉及规范的工程概念、科研方法、指标和缩写时，保留准确的专业名称，并在第一次使用时用一句通俗的话说明其含义及与当前问题的关系；必要时举一个贴近当前任务的小例子。不要为了口语化歪曲标准含义，也不要反复解释用户已经熟悉的术语；用户明确要求专业表述时按其要求调整。
- **先问是不是，再问为什么**：理解真实目标，核查问题前提与技术路线，不沿明显错误的实现盲目优化。
- **事实与结论分开**：以真实代码、运行记录和证据为准；不捏造测试、不隐藏失败、不把推断当事实。
- **保持实现干净**：按职责拆分代码；注释解释当前机制，尽量使用易懂的中文与准确的专业术语；避免过度设计、无关改动和层层叠补丁。必要时可重构，但必须符合当前任务的权限和工作模式。
- **恢复上下文，不擅自切换任务**：只有当前明确在处理某个 run 时才读取其 README 和相关证据；普通任务无需扫描 runs。历史对话和摘要不得代替真实文件、Git 状态和实验记录。始终按用户当前授权工作，**绝不从“任务需要管理”推断可以新建 run**。

### 8.1 已有代码通过 `.patch` 修改（两种模式通用）

`.patch` 是记录文件修改位置与内容、可检查并重新应用的补丁文件。**修改本次任务开始前已存在的代码时，通过保存的 `.patch` 文件应用修改，并维护反映最终方案的补丁；补丁只是修改与恢复方式，不增加操作授权。** 普通模式将补丁应用于当前项目的授权路径；run 模式仅应用于隔离工作区，直到用户明确授权正式落地。

- **保存位置**：run 的补丁保存在该 run 内；普通任务使用已有的相关任务资产目录或 `change/` 下按主题组织的资产位置，不为保存补丁新建 run、worktree 或并行状态文档。必要说明并入所属 README，简单任务无需额外报告。
- **基线明确**：记录准确 commit、补丁覆盖的文件和应用顺序。普通任务如有相关未提交修改，记录并保全任务开始前的相关文件状态，以该实际状态为修改起点；不得把用户已有差异计入本任务补丁，更不得为获得干净基线重置用户文件。run 的独立恢复另按第 3.4 节执行。
- **只交付最终修改**：探索时可以迭代补丁，最终须汇总为相对于记录起点的完整修改，不要求依次回放试错过程。补丁、代码、注释与报告都描述当前最终机制；淘汰方案和失败经验如需保存，放在明确标识的历史证据中，不混入最终方案。
- **应用与验证**：应用前在对应起点执行 `git apply --check`，通过后再执行 `git apply`，并核对实际 diff 与必要测试。该检查只证明补丁能应用，不证明功能正确；最终补丁还须能从记录起点重新应用。不得使用全工作区 diff 混入无关任务，不提交含凭据的补丁。
- **限定范围**：补丁要求仅适用于修改已有代码；新增实现文件直接完善到最终状态并单独保存，删除、重命名、报告和其他非代码文件操作不强制套用 `.patch`，但必须满足授权及必要恢复要求。本次任务新增的文件不再堆叠额外补丁。
- **适度审查**：核对补丁范围、可应用性、最终实现及报告一致性。是否需要独立子 agent 审查按第 5 节的实际风险和用户要求决定；不因采用补丁就强制增加审查轮次。

## 9. 本项目目录和事实入口

### 9.1 正式项目与探索run

| 路径 | 用途 |
| --- | --- |

普通模式使用上述正式目录；run模式在隔离工作区内使用同样的官方结构。算法×seed的引擎run不等于根级探索run，“开始跑实验”不授权创建新的根级run。已有历史探索与决策入口继续保留，不因新规范自动迁移、归档、清理或重新启动；根级runs索引将活跃探索与历史导航分开。仅在明确归档已有run时按需创建归档索引。

每份README只索引本级文件及直接子目录。正式实验状态在实验README，探索状态在对应run README；不要新建并行tracker/status/handoff，不在方案、报告中重复维护进度。

### 9.2 启动与恢复

1. 查看`git status --short`，辨认用户、其他任务及暂存区改动。读取根README；研究任务读取TOPIC和对应假设/实验README；只有当前run或相关历史决定需要时才查其记录，不扫描全部runs。
2. 从`.env`读取`PYTHON_PATH`，不输出密钥或完整环境文件。使用项目uv管理的解释器和依赖，不默认使用系统Python，不擅自重建环境。
3. 开始或恢复研究流程、阶段不明时使用只读入口：

```bash
PYTHON_PATH=$(sed -n 's/^PYTHON_PATH=//p' .env)
PYTHON_PATH=${PYTHON_PATH:-.venv/bin/python}
"$PYTHON_PATH" .agentsociety/bin/ags.py research-pipeline where-am-i --json
```

4. 解释器应能`import agentsociety2`并满足安装版本要求。通过import、registry（模块注册表）和实际入口核对加载来源，不用猜测源码路径代替运行时检查。
5. 机器阶段、实验实际运行与用户授权分别核对。文档冲突时检查实际入口、冻结配置、原始结果和已采纳决定，不按文件名或日期猜测；未解决冲突记录在所属README。

LLM配置为`AGENTSOCIETY_LLM_API_KEY`、`AGENTSOCIETY_LLM_API_BASE`、`AGENTSOCIETY_LLM_MODEL`；实际接口与模型以当前配置及冻结记录为准。凭据不进入报告、日志或Git。离线验收不调用LLM或偷偷联网；旧批运行授权不自动覆盖新批、更多数据或更高预算。

## 10. AgentSociety工作流与验证

### 10.1 按任务使用技能

优先`.agentsociety/bin/ags.py`及现有技能，不另造临时工具替代已有流程。先读取实际SKILL.md，具体命令以当前安装版本为准。

| 工作 | 技能 |
| --- | --- |
| 阶段定位、恢复与修订路由 | `agentsociety-research-pipeline` |
| 学术文献 | `agentsociety-literature-search`，按需用网络研究补充 |
| 模块选型、假设 | `agentsociety-scan-modules`、`agentsociety-hypothesis` |
| 外部数据检索、接入、共享发布 | `agentsociety-use-dataset`、`agentsociety-create-dataset`，按实际需求及授权使用 |
| 配置生成与检查 | `agentsociety-experiment-config` |
| 自定义Agent、环境模块 | `agentsociety-create-agent`、`agentsociety-create-env-module` |
| 已校验且已授权的运行 | `agentsociety-run-experiment` |
| 有实际输出后的分析 | `agentsociety-analysis` |
| 论文与内部审稿 | 当前可用论文工具、`agentsociety-paper-review`；不假设已经移除的内置paper仍可调用 |

配置、Agent或环境创建前核对人数、步数、运行时长/费用及复杂度预算。优先读取已有记录，缺失且影响方案时才问；规模未确定时给出2–3个有取舍的方案。实现、离线检查、LLM运行、扩大矩阵与采用探索成果分别核对授权，不重复索取已有授权，也不扩大其范围。

编码或实质代码审查时，按需读取实际Ponytail与Karpathy Guidelines技能，优先既有实现、标准库和最小必要修改。本地缺失时说明并查找可信来源，不假称已安装、不自动远程安装。中文注释说明模块职责、功能块、关键机制和单位/边界，保留必要专业术语；纯文档任务不启动代码审查或全栈构建。

### 10.2 流水线状态

控制agent在实际阶段完成或发生实质变化后通过CLI更新；普通文档整理不改变研究阶段。不要手改`.agentsociety/*.json`或`.jsonl`，除非已核实CLI无法完成并说明原因。控制agent是机器状态的单写者，审查、分析和审稿子agent不改状态。

已接受的阶段修订使用：

```bash
"$PYTHON_PATH" .agentsociety/bin/ags.py research-pipeline reroute STAGE \
  --reason "接受的修订原因" --source-artifact PATH
```

STAGE必须是实际支持的阶段，不能写`human_decision`、`none`或手写早期阶段来倒退。操作时明确hypothesis_id、experiment_id。技能中的“阶段更新后自动提交”“git add -A”不覆盖第2、7节；未获commit授权时不自动提交或暂存，交付说明未提交的状态变更。

### 10.3 配置与运行

- 正式机制放custom，配置生成器与参数放实验init；参数遵循官方schema（配置结构约定），Agent和环境参数放`kwargs`，`agent_id`与`kwargs.id`一致。生成后用官方入口校验，核对实际模块加载与必要的workspace恢复契约。
- 运行前冻结输入、参数来源、源码版本、配置、steps、指标、分类口径、矩阵、预算与停止/扩展条件。科学依据、工程经验、建模约定分别说明，不为漂亮曲线事后改变判据或隐藏失败。
- 正式入口为`"$PYTHON_PATH" -m agentsociety2.society.cli`；后台必须设置`--log-file`，明确`--config`、`--steps`、`--run-dir`、`--experiment-id`。配置准备与检查不授权启动。批量时核对包装器的输出/status/stop是否按run_id区分，防止覆盖不同条件。
- 遵守已冻结的顺序、预算、恢复与停止规则，不擅自重启失败或不一致checkpoint。以实际checkpoint、Agent workspace、replay及日志确认进度，不只看监督器文字；保全原始失败证据。
- 完整LLM仿真、数值代理、敏感性、未运行预测与失败/中断分开报告。现实内容类型和仿真作者类型核对同口径；纯排序比较与含候选池、生命周期、保底、回流差异的完整制度比较不能混称。

### 10.4 官方扩展与适度验收

自定义Agent、环境及技能按当前AgentBase/PersonAgent、EnvBase、`@tool`、ServiceProxy和registry接口实现，保持创建、保存、恢复及Ray调度契约。readonly标记应与实际副作用一致；自定义技能放custom/skills，遵循当前技能选择与激活流程，不照搬旧版技能链。

按第5节选择验证强度。custom修改先做相关功能测试；改动引擎才扩大到SDK检查，扩展/前端改动才做对应lint/build。依赖变更在所属uv工作区更新锁文件；扩展/前端用npm ci；测试按官方要求设置`MEM0_TELEMETRY=False`、`ANONYMIZED_TELEMETRY=False`。引擎源码开发前参考本地上游AGENTS和CONTRIBUTING，核对当前实际目录；远端以本项目git remote及用户指令为准。

完整论文内部审稿按paper-review技能：PDF先冻结审稿输入并通过质量门禁；正常流程委派三位隔离reviewer，再由单独MetaReview核实证据和分歧。评审只写评审包，不改研究产物、不跑实验、不更新流水线。这是特定论文评审流程，不是普通任务的强制独立审查。
