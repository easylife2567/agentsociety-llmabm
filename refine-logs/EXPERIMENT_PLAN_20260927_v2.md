# 仅修改真实帖子注入时机的最小方案

日期：2026-09-27。状态：设计提案，尚未修改仿真代码或运行新实验。

**最新范围裁定：用户目前只希望解决真实帖子注入时机。** 此文件替代v1的广泛重设计；v1中的新增算法臂、注入量/抽样调整、知识边界重构及重新校准全部退出当前任务。原依赖审计保留为背景，不代表每项都必须在本次实施。

## 1. 本次目的

将interest/random从“当周行动前注入整周真实样本”，改为“每条真实帖按published_at到达；Agent只能读取自己行动时刻已经到达的帖子”。保留每人每周一次行动及原有推荐/行为机制。

为了让当周不同发布时间真正影响不同人，必须为interest/random定义周内行动时点；如果所有人仍在周初读取一次，分时注入的当周内容无人能看到，相当于另一种周滞后模型。最小实现复用已有chronological冻结行动表，不重新估计作息、不新增行动机会。

本次比较准确名称是“真实帖可见时间及对应读取调度的修正”，不声称算法纯效应已经被识别，也不把其他既有局限一起修完。

## 2. 改动边界

| 项目 | 本次处理 |
|---|---|
| 每seed的250条真实样本及其文本、类型、周配额 | 完全复用，不重抽、不增减 |
| 官方讣告 | 复用唯一帖子及已有约定时间；此前不能注入或被置顶 |
| 推荐算法 | 原interest/random/chronological定义保留，不增加matched臂，不统一候选池 |
| 人口、人设、词表、D/R/B和门槛参数 | 保留，不重新校准 |
| Agent机会及feed大小 | 每周一次，最多10条；不足时按现有实际长度处理 |
| interest/random行动时刻 | 复用现有100人冻结周内小时表；同seed/各算法使用相同该表，不每周重抽 |
| 真实帖到达 | 按原published_at排序，到达时刻不晚于当前行动时刻才入池 |
| interest/random的Agent生成帖 | **继续在下一周才可推荐**，保留原有周级回流延迟 |
| chronological的Agent帖 | 保留原来的后续小时可见，本次不改 |
| 帖子life | 保留原周界更新、原半衰期和退场线，不改成连续小时衰减 |
| 帖级曝光饱和 | 保留原公式和确定性装配计账顺序，不额外增加新的同步机制 |
| 个人疲劳R | 每周仍一次实际阅读；按既有历史曝光口径更新，不每小时重复衰减 |
| 初始池/空feed | 不补入额外真实帖；沿用既有规则并记录空feed及短feed，避免为了凑10条引入另一个处理 |
| 周统计/监控 | 必要适配到达计数和引擎批次数，仍汇总11周 |

不能直接将interest/random整个切到chronological分支：那会同时改变Agent帖子回流、候选池、置顶/保底和生命周期，超出当前授权范围。

## 3. 执行顺序

1. 周开始，沿用原规则提交上周Agent帖子、执行原周级life更新，准备本周累计容器。
2. 推进到冻结表中的下一个有人行动的小时，把截至该时刻已发布且尚未注入的真实帖入池。
3. 对该小时行动者使用原算法装配feed；读取资格不得包含未来真实帖。原interest置顶/保底只能从已经到达的池中选择，不得借用本周完整样本。没有足够可用哀悼帖时不以未来帖子补齐。
4. Agent按原U公式决定是否发言；新帖加入“本周待提交”队列。本周后续小时仍不能看见这些Agent新帖，保持原周级延迟。
5. 每个Agent只行动一次。保存每人的feed及曝光；个人累计曝光按原周末口径提交，不按引擎批次数重复累计。
6. 周末处理最后行动之后、周界之前到达的真实帖，记入真实到达账；汇总本周行为，再进入下一周。

每个批次的真实注入游标必须可恢复，避免重启后重复注入。新的时间调度参数独立于推荐算法名；run_batch/monitor不能再认为random/interest必然只有11个引擎step。

## 4. 必须检查的连锁反应

### 4.1 时间和跨周

按现有小时实现把带offset的published_at换到上海时间比较。原week标签保持不改；新增/保留source_week与实际arrival_week的区分，不覆盖旧资产或重建benchmark。

已发现原资产按UTC分周、小时调度按上海时间；三个样本有6/1/2条发生周标签错位。新版资格只由时间决定，不能因source_week尚未轮到而延迟已发布帖子，也不能因source_week已到而提前注入。周末计数必须使用实际到达日志，并把这些跨周迁移单列；原周配额继续作为源样本审计字段，不能假定它等于实际入池周数。比较旧新Agent输出时统一仿真报告周边界，旧外部供给/效标的UTC口径保留说明，不把跨周差异隐去。

官方帖原文件没有published_at，沿用现有明确约定的2026-03-24 20:00上海时间，并在清单中标注为约定时间，不能声称它是实测抓取时间。

### 4.2 稀疏输入与事件响应

现有样本在W12早期可能尚无外部帖到达。记录实际空feed数、feed长度、首次真实到达时间。此处不改变样本量或增加预热池；如果空池影响非常大，作为本次结果报告，后续另议。

W13官方帖及晚些时候到达的悼念帖不能再影响此前已行动的人。置顶/保底实际覆盖人数下降是本次时间修正的后果，不为维持旧峰值补发或增加行动。

### 4.3 参数与推荐状态

life仍按周，R仍按个人曝光次数。真实帖在一周内陆续入池，会改变之后行动者的候选组成；此前小时累积的真实曝光饱和也会影响后续推荐。这些是按时阅读下的运行结果，不另外修改饱和参数或生命周期公式。

本次不解决所有前视信息：既有人设、词库和整周环境文字可能仍影响生成。验收目标是“未来真实帖子不能出现在feed中”，不能扩大为“LLM完全不知道未来”。原依赖审计中的知识风险保留记录，退出这次实施范围。

### 4.4 统计与恢复

仍应有11个周度env结果、100×11次Agent行动机会；不能误把小时批次数当周数或让Agent重复行动。真实帖入池总数、实际入池周、每条首次可见时间、重复注入数需要独立日志。

get_feed读取既有行动快照，不因为重复查询增加曝光；周末不要再对已提交的批次曝光重复计数。恢复时保存真实帖游标、本周Agent待提交队列、已行动集合和曝光累计。旧checkpoint不能不加版本检查地复用于新调度。

## 5. 验证和最小重跑

先做无LLM用例：周初/周中/周末真实帖、同一时刻发布、跨UTC/上海周界、官方帖尚未到达、同周Agent帖仍不可见、次周Agent帖可见、重复get_feed、恢复与未中断执行一致。

验收不变量：

- 每个实际feed中的真实帖published_at≤该Agent行动时刻。
- 三份输入仍各250条且源id/正文hash完全不变；完整窗口结束后各帖恰好入池一次（窗口外时间异常必须先明确处理，不静默提前或丢弃）。
- 每agent每周最多一次行动与一次发帖机会；最多10条feed，曝光计数不随空小时增加。
- interest/random当周生成帖在本周其余小时不可推荐。
- 推荐参数、人口、行为参数、原样本及chronological配置不变。
- 11周汇总、真实到达及Agent产出守恒，checkpoint恢复等价。

工程烟测：interest/random各seed0，先W12–W14，合计最多600次行动机会。通过后只重跑这两个受影响算法的3个seed，共6次完整运行、6,600次行动机会；旧结果用于配对比较，chronological沿用已有结果。正文实际调用数随发言数变化，路由/重试另计。尚未启动任何运行。

对比指标仅回答时间修正的影响：未来帖曝光违规、空feed/短feed、实际真实帖到达、W13响应覆盖、Agent分类型绝对产出及份额、旧新配对轨迹。参数不重新拟合，不能为了复现旧图修改数据或规则。

预期：事件响应不再提前获得整周真实内容；W13峰和晚期变化可能后移或减弱，但兴趣选择、历史库存和曝光疲劳可能抵消，方向以重跑为准。由于本方案保留Agent次周回流，不会把新增的周内Agent级联误当成真实帖注入时机的效果。
